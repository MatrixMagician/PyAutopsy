<objective>
Fix the root-level deleted-file misclassification (UAT gap, RECOV-02): every deleted file in a
volume's ROOT directory is wrongly flagged `is_orphan=True`, emptying the report's "Recovered
Files" section and dumping root deletions into "Orphan Files" with the false provenance claim
"parent directory is itself gone".

Root cause: `walk_fs()` yields root-level entries with `parent_addr=None`, and
`iter_deleted_inodes()` computes `parent_known_orphan = (parent_addr is None or parent_addr not in
alloc_inodes)`. `None` is OVERLOADED — it means BOTH "root-level entry" (walk_fs default) AND "no
surviving dir link" (the genuine pass-2 range-scan orphan deliberately set around filesystem.py:524).
The root directory is always allocated, so a root-level deletion is NOT an orphan.

Fix direction (from the diagnosis): tag root-level entries in `walk_fs` with the real root inode
(`int(fs.info.root_inum)`) so a deleted file in root carries an allocated `parent_addr` and
classifies as recovered; reserve `None` ONLY for the genuine no-dir-link orphan. Add a regression
fixture + test (FAT + ext4) covering BOTH a root-level deletion (Recovered) and a removed-parent
deletion (Orphan). Keep the genuine-orphan detection (NTFS resident-deleted pass-2 path; parent
inode genuinely unallocated) intact.

Purpose: restores forensic correctness — recovered root-level deletions are reported as Recovered,
not falsely claimed orphaned (overclaim, against D-32/RECOV-03). The committed fixtures + the
determinism gate missed this precisely because no committed fixture had a root-level deletion.

Output: a corrected seam, an updated walk-fake test helper, a new root-deletion regression fixture
(reusing the existing committed-image pattern), and a regression test that pins both directions.
</objective>
